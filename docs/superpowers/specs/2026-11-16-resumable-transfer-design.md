# 斷點續傳設計

日期：2026-11-16
狀態：草稿，等待確認

## 1. 目的與背景

使用者在兩支 Android 手機之間傳檔，傳到一半時傳送端回報
`Connection timed out (os error 110)`，接收端停在半途。按傳送端的「重送」也一定失敗。

原因（已從程式碼確認）：

- LocalSend v2 協定每個檔案只用一次 `POST /api/localsend/v2/upload`，本體是整個檔案，沒有任何「從第幾個位元組開始」的機制。
- 接收端在連線中斷時把檔案標成 `Failed`（`packages/core/src/http/server/v2.rs` 的 `finalize_file`），只有檢查碼不符才會回到 `Pending`；唯一的檔案失敗時整個工作階段結束。重送請求因此一律得到 403 `Invalid token or IP address`。
- 接收端還沒發現斷線時，檔案停在 `InProgress`，重送一樣被拒。
- 上傳只接受與 prepare-upload 相同來源 IP 的請求，傳送端換了 IP 也會被擋。

使用者會長期使用這個軟體，要的是**真正的續傳**：從斷掉的位置接著傳，而且要涵蓋「App 被關掉、手機重開、任一方按了取消」之後再傳同一個檔案的情況。

LocalSend 官方對續傳有多個功能請求（localsend/localsend#1191、#2820、#2824、#2934、#3682），都沒有實作；v3 協定草案也沒有續傳。所以這是本分支自己的協定擴充，必須和官方版裝置相容。

## 2. 目標、非目標、反目標

### 目標

1. 兩台都裝本分支 App 的裝置之間：
   - **暫時斷線**（Wi-Fi 斷一下、換基地台、傳送端 IP 改變）：傳送端自動重連，從斷點接著傳，使用者不用操作。
     接收端 IP 改變時，自動重連會在 5 分鐘後放棄；使用者重新傳送時由跨傳輸續傳接手（實作者決定，理由：同一個 Wi-Fi 下手機重連通常拿回同一個 IP，為少見情況新增跨隔離區的位址查詢不划算）。
   - **跨傳輸續傳**：任一方 App 被關掉、手機重開、任一方按了取消之後，只要把**同一個檔案**再傳給**同一台**，就從上次確定收到的位置接著傳。
2. 續傳完成的檔案一定經過整檔 SHA-256 驗證，不符就從頭重傳。
3. 接收端的半成品不會以正式檔名出現在下載資料夾或相簿裡。
4. 介面上看得出「正在重新連線」「將從 X% 接續」。

### 非目標（這次不做）

- `web-peer/`（Node.js 電腦端）的續傳。它和本分支 App 互傳時照舊整檔傳送；之後另案補上。
- 網頁分享（瀏覽器下載）與下載 API 的續傳。
- 與官方版 LocalSend 之間的續傳（官方版不懂這個擴充，照舊整檔傳送）。
- 分塊檢查碼、多條連線並行傳同一個檔案。
- 管理半成品的介面（列出、手動刪除）。半成品靠到期自動清除。
- 文字訊息（用 `preview` 傳送的那種）的續傳。
- iOS 與桌面版的實機驗證。程式碼是共用的，但只保證 Android。

### 反目標（就算功能能動，發生了也算失敗）

- 產生內容錯誤卻被當成完整的檔案。
- 和官方 LocalSend 裝置互傳時出現任何退步。
- 別台裝置能把資料寫進不屬於它的半成品，或藉此讀到半成品內容。
- 半成品無限累積、塞滿手機空間。

## 3. 限制

- 官方版接收端會忽略 JSON 裡看不懂的欄位（`PrepareUploadRequestDtoV2` 等沒有 `deny_unknown_fields`），官方版傳送端也會忽略回應裡多出來的欄位，所以可以用新欄位協商。
- 傳送端「計算檢查碼」與接收端「驗證檢查碼」兩個設定預設都是開的（`persistence_provider.dart` 的 `getCreateChecksums`、`getVerifyChecksums`）。
- 接收端目前同時只能有一個上傳工作階段（`v2.session` 單一槽位）。
- 存檔目標由 Dart 決定、由 Rust 寫入：一般路徑，或 Android 儲存空間存取框架（SAF）的檔案描述符；存到相簿時先寫快取檔再搬進相簿。
- Android SAF：`createDocument` 遇到同名會自動改名；目前用 `"wt"` 開檔（會清空）。只有 `"rw"` 保證拿到可以 seek 的檔案；`"wa"` 是附加模式，seek 無效；不支援的模式 Provider 會丟 `UnsupportedOperationException`。
- 修改 FRB 介面後必須重新產生綁定（`flutter_rust_bridge_codegen generate`）。
- 這台 Mac 目前沒有 Rust、Flutter、Android SDK；過去 APK 是在 Windows 上編的（見 README）。

## 4. 做法比較

| 做法 | 內容 | 優點 | 缺點 |
|---|---|---|---|
| **一、位移量續傳（採用）** | 在現有 prepare-upload／upload 上加能力協商與起始位置；新增查詢已收位置的端點 | 改動集中、向下相容；預設就有的整檔 SHA-256 正好用來驗證 | 損壞要到最後才發現，發現後整檔重傳（實際很少發生） |
| 二、固定區塊傳送 | 檔案切塊，每塊有自己的檢查碼，只補缺漏或損壞的塊 | 損壞代價小，未來可並行 | 協定與狀態管理複雜很多，工程量約兩倍 |
| 三、照搬 IETF 草案／tus 端點 | 建立上傳資源、HEAD 查位置、PATCH 附加 | 標準化 | 和 LocalSend 既有的工作階段、權杖、憑證驗證重疊，要維護兩套授權；草案仍在變動（-15 版） |

使用者把「怎麼做」交給實作者決定；採用做法一。語意上借用 IETF 草案（draft-ietf-httpbis-resumable-upload-15）與 tus 1.0：
- 已收位置只算「確定寫進儲存裝置」的位元組，而且不會倒退。
- 位置不符時回 409，並附上正確位置。
- 舊的上傳請求還沒結束時，伺服器可以主動切斷它。

## 5. 設計

### 5.1 協定擴充（第 1 版）

所有新欄位與端點只在**雙方都表明支援**時使用。

**能力協商**

- `POST /api/localsend/v2/prepare-upload` 的請求本體新增 `"resumeSupport": 1`。
- 接收端支援時，回應本體新增：
  - `"resumeSupport": 1`
  - `"resumeOffsets": { "<fileId>": <已收位元組數> }`：只列出位置大於 0 的檔案。
- 傳送端只有在回應帶 `resumeSupport` 時，才使用下面的參數與端點。
- 官方版傳送端不會送 `resumeSupport`，接收端就完全照現在的行為處理（直接寫正式檔名、斷線即失敗）。

**上傳帶起始位置**

- `POST /api/localsend/v2/upload?sessionId=…&fileId=…&token=…&offset=N`
- 本體是檔案第 N 個位元組到結尾的內容（長度 = `size - N`）。
- 沒有 `offset` 時等同 `offset=0`。
- N 必須等於接收端目前記錄的已收位置，否則回 **409**，本體是 `{"message": "Offset mismatch", "offset": <正確位置>}`。
- `offset > 0` 時，這個檔案一定要有 `sha256`（見 5.6）。

**查詢已收位置（新端點）**

- `POST /api/localsend/v2/upload-offset?sessionId=…&fileId=…&token=…`，回 200 `{"offset": N}`。
- 副作用：如果同一個檔案還有一個舊的上傳請求在進行（接收端還沒發現斷線），接收端先中斷它，等它把資料寫進儲存裝置、記下位置之後才回應。所以用 POST 而不是 GET。
- 檔案已完成時回 200，`offset` 等於檔案大小，傳送端直接把它當成完成。

**身分驗證**

- 續傳**只在加密模式**（HTTPS，雙向憑證）提供。未加密模式下，接收端不回 `resumeSupport`，傳送端也不送，行為和現在完全相同（實作者決定，理由：未加密時只有對方自報、可以偽造的指紋，用它當半成品的鍵會讓同網段的人冒名接續或清掉別人的半成品；加密模式是預設值）。
- 支援續傳的工作階段改用**傳送端憑證指紋**驗證 upload、upload-offset、cancel，不再要求來源 IP 相同，傳送端換 IP 後仍能續傳。
- 官方版傳送端的工作階段維持比對 IP。

### 5.2 接收端工作階段生命週期（Rust：`packages/core/src/http/server/`）

- `FileStatusV2` 新增 `Interrupted`。每個檔案記錄 `committed`（確定已寫入的位元組數）。
- 支援續傳的工作階段：
  - 上傳中途中斷時，檔案改為 `Interrupted`，**工作階段不結束**。
  - 工作階段結束的時機：
    - 所有檔案都完成或失敗。
    - 任一方取消。
    - 閒置逾時：沒有任何上傳在進行，持續 **5 分鐘**。逾時後 `Interrupted` 的檔案改為 `Failed`，但半成品保留給跨傳輸續傳。
  - 閒置等待期間，其他裝置的 prepare-upload 照舊收到 409（忙碌）。
  - **同一個傳送端**（憑證指紋相同）送來新的 prepare-upload 且帶 `resumeSupport`，**而且請求中包含舊工作階段裡還沒完成的同一個檔案**（SHA-256 與大小相同）時，舊工作階段結束（新的結束原因：被取代）。這個情況代表傳送端的 App 重開過，或使用者重新傳送。
    - 取代前先中斷舊工作階段進行中的上傳，並等它們收尾（最多 10 秒，逾時回 409），舊的寫入器才不會和新的工作階段同時寫同一個半成品。
    - 同一個傳送端的其他請求（例如傳一則文字訊息）照舊收到 409，不會中斷正在等待重連的傳輸。（最終審閱後修正：原規則會讓任何新請求中斷進行中的傳輸。）
  - 可續傳的工作階段被任一方取消時，進行中的上傳一併中斷（非續傳工作階段維持原行為：跑完為止）。
  - 可續傳工作階段中，**沒有 `sha256` 的檔案不續傳**：中斷即失敗，App 給的起始位置也忽略。
- 檢查碼不符：位置歸零、刪掉已收內容，沿用現在的重試上限（`MAX_UPLOAD_ATTEMPTS`）。
- 新增給 App 的事件（擴充 `ServerEventV2`，不另開管道）：
  - 檔案中斷，附 `committed`。
  - 已收位置更新（節流）。
  - 工作階段因閒置或被取代而結束（`SessionEndReasonV2` 新增對應原因）。
- `PrepareUploadDecisionV2::Accept` 改為可附每個檔案的起始位置：由 App 決定要不要續傳、從哪裡續傳；Rust 只負責驗證與執行。

### 5.3 半成品登記簿（Dart：伺服器隔離區）

- 由伺服器隔離區管理，存成 App 私有目錄下的 JSON 檔，例如 `<應用程式支援目錄>/resume/partials.json`。
- 每筆紀錄包含：
  - 傳送端憑證指紋
  - 檔案的 `sha256`、大小、原始檔名
  - 半成品位置：路徑，或 SAF 的 document URI
  - 預定的最終目的地：資料夾、是否存相簿
  - 已確定寫入的位元組數
  - 建立時間、最後更新時間
- **只有帶 `sha256` 的檔案才會登記**；沒有檢查碼就無法確認是同一個檔案，也無法驗證拼接結果。
- **比對**：在 Rust 送出 PrepareUpload 事件時查詢。同一個傳送端憑證指紋、同一個 `sha256`、同一個大小，而且半成品還存在，才算比對到。
  - 起始位置 = 登記的確定位元組數與實際檔案長度兩者取小。
  - 比對結果附在給主隔離區的 prepare-upload 事件上，讓接收畫面顯示「將從 X% 接續」；使用者接受後，跟著決定一起交給 Rust。
  - **接受時再確認一次存放設定**（實作者決定）：使用者可能在確認畫面改了目的資料夾或「存相簿」開關。伺服器隔離區收到接受決定時，如果這次的目的資料夾或存相簿設定和半成品登記的不同，這個檔案改從 0 開始，寫到這次的目的地；舊半成品留到到期。理由：跨資料夾搬移（不同 SAF 資料夾之間只能整檔複製）的工作量和失敗情境都多很多，而這種情況很少見。此時畫面上先前顯示的「將從 X% 接續」可能不準，可以接受。
  - **正式檔名用這次的名稱**：完成時改成這次工作階段決定的檔名（接收端改過名就用改過的），在半成品所在的資料夾處理同名衝突。
- **更新**：Rust 回報確定位置時（節流，例如每 16 MiB 或每 5 秒一次，中斷時一定回報一次），登記簿跟著更新。
- **完成**：檔案驗證通過並改成正式檔名之後刪除紀錄。
- **取消或拒絕**：半成品保留，不刪除。
- **到期**：最後更新超過 **7 天**的紀錄連同半成品一起刪除。伺服器啟動時和每次收到 prepare-upload 時各清理一次；半成品檔案已經不存在的紀錄也一併刪除。
- 以傳送端憑證指紋為鍵，其他裝置無法接續或覆寫別人的半成品。

### 5.4 半成品存放與完成（接收端）

只有支援續傳的工作階段使用新流程；官方版傳送端維持現狀。

- **一般路徑**：在目的資料夾寫入隱藏的暫存檔 `.<正式檔名>.<登記編號>.lspart`（含登記編號：同一次傳輸可能有同名的檔案）。完成驗證後，在同一個資料夾改名為正式檔名；此時才處理同名衝突（自動加編號）。Android 一般路徑在改名後照舊呼叫媒體掃描。
- **SAF**：用 `createDocument` 建立暫存名稱的文件，記下它的 document URI。
  - 續傳時用 `"rw"` 重新開啟同一個 URI（新增 method channel），不能再呼叫 `createDocument`。
  - 完成時用 `DocumentsContract.renameDocument` 改成正式檔名（新增 method channel）。
  - Provider 不支援改名時，退回「一開始就用正式檔名」的現行做法；續傳照樣可以，只是半成品看得到。
  - `"rw"` 開不了時，這個檔案放棄續傳，從頭整檔重傳。
- **存相簿**：半成品放在快取資料夾。完成後照現在的流程搬進相簿，再刪掉快取檔。快取被系統清掉時，登記簿比對不到檔案，就從頭傳。
- 檔案時間戳記在完成時套用，和現在一樣。

### 5.5 寫入器（Rust：`common/save.rs`）

- `FileUploadTarget::Path` 與 `Fd` 新增 `offset`：
  - **Path**：開檔時不清空，截斷到 `offset`，再移到 `offset` 開始寫。
  - **Fd**：描述符必須由 Dart 以 `"rw"` 開啟。截斷到 `offset`（盡力而為），再移到 `offset`。
- 需要驗證檢查碼且 `offset > 0` 時，先從目標檔讀回前 `offset` 個位元組，用來初始化 SHA-256；讀不回來就讓這次上傳失敗，並把位置歸零。
- 每寫入約 16 MiB 呼叫一次 `sync_data`，並回報新的確定位置（只在可續傳的工作階段；與官方版互傳時不額外同步，維持原本的效能）。
- 讀回前段時要能被中斷（大檔讀回可能很久，不能卡住傳送端的重連）。
- 中斷時先 flush、`sync_data`，把檔案截斷到確定位置，再回報。
- 進度事件改成回報**絕對位置**（`offset` + 這次已寫入），介面顯示真實進度。
- `Stream` 目標（App 自己接收位元組）不支援續傳。

### 5.6 傳送端

**Rust 客戶端（`packages/core/src/http/client/`）與 FRB 介面（`packages/localsend_isolates/rust/src/api/http.rs`）**

- `upload` 新增 `offset`。
  - `FileContent::Path`：開檔後移到 `offset`。
  - `FileContent::Fd`：用 `lseek` 移到 `offset`；描述符不能 seek 時（例如管線），讀掉前 `offset` 個位元組。
  - `FileContent::Stream`：丟掉前 `offset` 個位元組。
  - 進度從 `offset` 起算。
- 新增 `upload_offset` 呼叫。
- prepare-upload 的請求帶 `resumeSupport`，並解析回應的 `resumeSupport` 與 `resumeOffsets`。
- 409 的回應本體要解析出 `offset`。
- 改完重新產生 FRB 綁定。

**上傳隔離區（`upload_isolate.dart`）**

- 第一次上傳就從 `resumeOffsets` 給的位置開始。
- 如果發生連線層級的錯誤（連不上、逾時、連線被重設、本體送到一半失敗），而且接收端支援續傳：
  - 用退避間隔自動重試：1、2、4、8、15、30 秒，之後每 30 秒一次，總共最多 **5 分鐘**，和接收端的閒置逾時一致。
  - 每次重試先呼叫 `upload-offset` 取得位置，再從那裡上傳。
  - 收到 409 就改用回應裡的位置，馬上再試。
  - 收到 403 或 404（工作階段已經不在）就放棄，把檔案標成失敗。使用者重新傳送時，跨傳輸續傳會接手。
  - 收到 422（檢查碼不符）就從 0 開始，沿用現有的次數上限。
- 新增「重新連線中」事件（附重試次數），讓介面顯示。
- 傳送端進度頁上手動的 ↻ 重送，也走同一套流程：先查位置，再續傳。
- 傳送端關閉「計算檢查碼」時，不送 `resumeSupport`，整個傳輸照舊行為。

### 5.7 介面與文字

- **傳送端進度頁**：每個檔案可以顯示「重新連線中…（第 n 次）」；續傳的檔案進度從原本的位置開始。
- **接收端**：
  - 確認接收的畫面：可以續傳的檔案標示「將從 X% 接續」。
  - 進度頁：檔案中斷時顯示「等待對方重新連線…」，取消按鈕照常可用。
- 新字串加入 `app/assets/i18n/` 的英文（基準語系）與繁體中文；其他語系依現有慣例列入 `_missing_translations_<locale>.json`。重新執行 `fvm dart run slang`。

### 5.9 測試與驗證

- **Rust 整合測試**：新增 `packages/core/tests/v2_resume.rs`，沿用 `v2_server.rs` 的測試輔助函式。至少涵蓋：
  - 能力協商：只有雙方都支援、而且是加密模式時才出現新欄位。
  - 帶位置上傳、位置不符回 409 並附正確位置。
  - 中斷後查詢位置；舊請求還在進行時被中斷、接手。
  - 換 IP 但憑證相同時可以續傳；換憑證時被拒。
  - 續傳後整檔 SHA-256 正確；前段內容遭竄改時驗證失敗、位置歸零。
  - 閒置逾時；同一個傳送端的新 prepare-upload 取代舊工作階段。
  - 官方版行為不變：不帶 `resumeSupport` 時，斷線仍是失敗、仍比對 IP。
  - 寫入器：截斷、移位、`sync_data`、中斷時截斷到確定位置。
- **Dart 單元測試**：
  - 登記簿：比對、到期清理、檔案不存在的紀錄清理、只登記有檢查碼的檔案、接受時目的地不同改從 0 開始。
  - 上傳隔離區：重試與退避規則、409 與 403 的處理。
- 檢查項目照 AGENTS.md：`cargo test --features full`、`cargo clippy --features full`、`fvm dart format`、`fvm flutter analyze`、`fvm flutter test`。
- **實機測試**（兩支 Android 手機，傳一個數百 MB 的檔案）：
  1. 傳到一半關掉接收端 Wi-Fi 再打開。
  2. 傳到一半強制關閉傳送端 App，再重新傳同一個檔案。
  3. 傳到一半重開接收端手機。
  4. 傳到一半按取消，再重新傳。
  5. 存相簿與 SAF 自訂資料夾各做一次。

  每次都比對兩邊的 SHA-256，並確認下載資料夾沒有留下暫存檔。
